The dashboard, explained

A page that shows every app, its releases and what just happened. It has no server of its own: a script writes one small data file, and the page draws it.

1 The page, part by part

  1. Overall status. “all good” unless an app’s most recent real event failed; then “needs a look” plus the app names. From attention.
  2. App and hold state. One card per app. The chip says live, or on hold after a rollback. From apps[].name and apps[].held.
  3. Live release. The release folder current points at, plus the commit if a webhook deployed it. From apps[].live and apps[].deployed.
  4. Release history. One dot per kept release, oldest to newest. The filled, ringed dot is the live one. From apps[].releases[].
  5. A command to copy. The page never changes anything. It shows the exact rollback (and unhold) command for you to run. The app name is checked against ^[a-z0-9-]{1,40}$ first.
  6. Recent activity. The last 40 lines of the deploy log, newest first. From events[].

2 Where the data comes from

Why compare first? Each refresh builds the data again and only deploys if something other than the timestamp changed. Otherwise every deploy would also create a new dashboard release.

4 Why it is safe to show

It can only look

There is no write endpoint. The Copy button puts a command on your clipboard; you run it yourself.

Log text stays text

Log lines contain build output, so the page uses textContent only and never builds HTML from data. A line with <script> in it shows as plain characters.

Strict parser

A log line that does not match the exact format (or has a bad app name) is dropped. Details are cut to 120 characters.

Nothing leaves the page

No fonts, scripts or images from elsewhere. It works with the network cable pulled.

One honest limit: Caddy is bound to your Wi-Fi address for phone testing, so everyone on that network can see this page.

5 A bug worth knowing: the page that listed itself

before it listed every app, itself included

after it leaves itself out

The data now describes only the other apps, so it has nothing about the dashboard’s own release. A refresh with no real change prints “dashboard is up to date” and deploys nothing.

Takeaway. Anything that reports on a system and is also part of it can end up changing what it is measuring. Leave the observer out of the picture.

Try it

Run from the repo folder, inside WSL.

# rebuild the data and redeploy, even if nothing changed
python3 scripts/dashboard.py --force

# the same thing again: nothing changed, so nothing is deployed
python3 scripts/dashboard.py
dashboard is up to date (nothing changed)

# write the site into a folder to inspect it, without deploying
python3 scripts/dashboard.py --out /tmp/dash
cat /tmp/dash/data.json

Then open http://dashboard.localhost:8080, or on your phone the same name ending .192-168-40-241.nip.io:8080.
