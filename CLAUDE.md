# mini-deploy: notes for agents

A small self-hosted deploy platform, built in stages to **learn** how deploy platforms work: `git push` → webhook → build → new release folder → `current` link flips → Caddy serves the site.
Plan and diagrams: `Obsidian/Projects/claude add-ons/agent-patterns-and-deploy-platform.md`. Project note: `Obsidian/Projects/Mini Deploy/Mini Deploy.md`.

## Owner's working style

- **Teach + build.** For each step: explain the idea in 2-4 plain sentences, build it, then give the owner the test command to run themselves. Short "why" comments in the code.
- List and discuss changes first. Build only after the owner says **"go"**.
- One stage per session. Use `/stage N`.
- Never expose anything to the public internet (port forwarding, firewall rules, a real domain, tunnels) without the owner asking.
- Never install software without asking first (apt, Docker, Caddy, pip packages).

## Environment

- Windows 11 + **WSL2 Ubuntu** (distro name `Ubuntu`). All server pieces run inside WSL. Use the `wsl-run` skill for every command.
- Repo on the Windows side: `C:\Users\indra\Code\mini-deploy` (= `/mnt/c/Users/indra/Code/mini-deploy` in WSL). The owner uses GitHub Desktop; `git` isn't on the Windows PATH.
- Runtime data lives in the WSL filesystem, **not** on `/mnt/c`: `/sites/<app>/releases/<id>/` + `/sites/<app>/current` symlink. NTFS symlinks and permissions behave differently.
- Installed in WSL (2026-10-11): git, python3, tmux, caddy 2.11.7, docker 29.9.0 (Engine, from Docker's apt repo). The apt `caddy` systemd service is **disabled** (port 80, /etc/caddy). Ours is `mini-deploy-caddy` (port 8080, see Status 2026-10-12). Tailscale 1.104.1 (2026-10-12).
- Language for our own code: **Python 3, standard library first** (http.server, hmac, hashlib, subprocess, json). Shell only for tiny glue scripts.

## Security rules (the reviewers check these)

- App names: `^[a-z0-9-]{1,40}$` only. Never build paths or shell commands from unchecked input.
- No `shell=True`; pass argument lists to `subprocess`.
- Webhooks: check `X-Hub-Signature-256` with `hmac.compare_digest` **before** reading anything else. Secret comes from an env var, never committed.
- Switch the `current` link atomically: `ln -sfn` into a temp link, then `mv -T`. Keep at least the last 3 releases for rollback.
- Secrets go in `.env` (gitignored). Never print them.
- Never publish links, special files, `.env*`, `.git`, `.npmrc`: `deploy.py` checks the source **and the private copy it publishes**. Release = at most 500 MB, setuid bits stripped.
- Builds run as uid 1000, read-only root fs, caps dropped, image pinned by digest, npm scripts off, `.env` never copied in. Same-app builds are serialized (`.build.lock`).
- Caddy's admin API is a root-only unix socket (`/run/caddy-admin.sock`), never TCP. Dotfiles are never served.
- Webhook (`scripts/webhook.py`): loopback only (config refuses anything else). Order: path, size (1 MB), raw body, `X-Hub-Signature-256` via `hmac.compare_digest`, and only then parse. Every failure is the same bare 401. App, branch, URL and sub-folder come from `config/webhook.json`, never the payload, with one exception: for a repo with `"previews": true`, the branch of a push to a non-main branch comes from the payload, is read only after the signature check, must pass `safe_branch()`, only reaches git as a list argument after `--`, and is never logged (only the site name made from it); `after` must be 40 lowercase hex; each `X-GitHub-Delivery` is acted on once (ids persist in `/var/lib/mini-deploy/deliveries`). A valid signature is not proof of freshness: the worker builds a commit only if it is still the branch tip (`git ls-remote`), and skips one that is already live. Whole request has a 20 s deadline and at most 16 handlers. Secret is `WEBHOOK_SECRET` in `/etc/mini-deploy/env` (mode 600, root, parsed by Python, never sourced as shell), popped from the environment so children never inherit it. After a rollback the app is on hold: webhook pushes are skipped and logged `held` until `deploy.py unhold <app>` (a manual deploy or build also lifts it). Opening the webhook to the internet (tunnel) is the owner's decision.
- Previews: site name `<branch>--<app>` from `deploy.preview_name()` (cleaned, plus an 8-hex hash of the real branch when cleaning changed it; 4 hex was collidable on purpose). The real branch is stored in `/sites/<preview>/.branch`; a build or delete for another branch is refused (`check_preview`, `remove_preview(name, branch)`). Only previews may contain `--`: `deploy.py deploy`, `build.py` and the webhook config refuse it in app names, and `deploy.py remove` accepts nothing else (checked 2026-10-12: no older app has `--`). At most 10 previews per app (only folders with `releases/` count; a failed first build's empty folder is removed by `drop_if_empty`), 2 releases each. Deletion: folder must exist, then `git ls-remote` (exact ref match, `remote_tip`) must show the branch is gone. Locks: always `.build.lock` before `.lock`; `locked` refuses if the folder was removed while it waited. Webhook queue: at most 20 different previews waiting (more get 503), live apps always taken first, a busy retry never replaces a newer job, `pending.json` that cannot be read is moved to `pending.bad`. **Owner decision (2026-10-12): with previews on, every branch pushed by anyone with write access is built and shown on the Wi-Fi; fine while the owner is the only one who can push. With collaborators, add a branch-prefix allowlist.**
- Env values (`scripts/appenv.py`): `/etc/mini-deploy/apps/<app>.json` (dir 0700, files 0600, root; both checked with lstat/fstat: real folder/file, ours, closed to others, else the build stops). JSON parsed by Python, never sourced, at most 1 MB (bigger = refused, not cut), written `ensure_ascii=False`; opened `O_NOFOLLOW|O_NONBLOCK` (a FIFO cannot hang it). Values come from stdin or a hidden prompt, never argv; `list` never prints a secret. **Only `npm run build` gets them**: `npm ci` runs in a separate box with no values (two `docker run`s sharing `/app`, one TIMEOUT). Into Docker as `-e KEY` (name only); the docker client gets a small environment (PATH, HOME, LANG, LC_ALL, TZ, DOCKER_*) plus the values, never argv. Values are read after `.build.lock` is taken. Secrets (default, >= 8 chars) are masked `[hidden]` in build output, logs and errors, as written AND in common encodings (JS/JSON string incl. `\uXXXX` and `<\/`, HTML, URL, base64 plain/URL-safe at all 3 alignments; forms < 8 bytes skipped), also across the 64 KB read limit; a build whose `dist/` (content or names) contains one is refused (dist over 500 MB refused before reading; scan errors = BuildError). **This is a safety net, not a wall**: code that hides a value on purpose gets past it; root and `docker inspect` can read values. `--public` values are not masked and may be published. Previews read only `<app>.preview.json`, never the live values. Keys `^[A-Z_][A-Z0-9_]{0,63}$`; refused: `PATH`, `HOME`, `TMPDIR`, shell vars (`ENV`, `BASH_ENV`, `IFS`, ...), prefixes `NODE_` (except `NODE_ENV`), `NPM_`, `NPM_CONFIG_`, `YARN_`, `PNPM_`, `COREPACK_`, `LD_`, `DOCKER_`, `SSL_`, `OPENSSL_`, `CURL_`, `GIT_`, `XDG_`, `PYTHON`, and `*_PROXY`. Error texts put key names after `nothing was deployed:` (dashboard and log header cut there; dashboard words `env problem`, `refused: secret in output`). An env-file error (`EnvBuildError`, `config = True`) stops the webhook's fallback chain. Build log header `env:` lists names only. Tests need `MINI_DEPLOY_APP_ENV` **and** `MINI_DEPLOY_TESTING=1` to move the store (the variable alone is ignored).
- Admin page (`scripts/admin.py`, `web/admin/`, systemd `mini-deploy-admin`, 127.0.0.1:9300): Caddy `@admin` = Host exactly `admin.localhost:8080`, `remote_ip` loopback, no proxy headers (same gate as logs); `admin` is a reserved app name. **"PC only" is not "only me"**: every program on the PC can reach :9300 directly, so the server checks everything itself: exact Host (DNS rebinding), password (scrypt, set ONLY from WSL with `admin.py set-password`, min 12), cookie `__Host-md_admin` (HttpOnly, Secure, SameSite=Strict, Path=/, no Domain; only its sha256 stored), CSRF header, Origin exactly `http://admin.localhost:8080`, `Sec-Fetch-Site` same-origin, JSON only, `Content-Length` digits 0..16 KB. Sign-in: each try is counted before the password check in one `BEGIN IMMEDIATE` transaction (parallel guesses all count); 5 free per hour, then 30 s doubling to 15 min; at most 2 scrypt checks at once; `admin.py unlock` clears it; sign-ins go to their own `logins` table, never the audit. Sessions: idle 12 h (the page's 30 s poll does NOT count as activity), max 7 days; new password signs all out. Actions rollback / rollforward need `expect` = the live release the page showed (a double click or retry is refused 409, never two steps back), lock wait 15 s; every error is answered (500) and audited. `deploy.rollback/rollforward` set the hold BEFORE the flip (a failed flip takes a new hold back). `deploy.deploy(refuse_if_held=True)` (the webhook's build path) re-checks the hold under the deploy lock, so a rollback made during a build is never undone (logged `held`). Server: 32 connections max (more = 503), 30 s per request. Unit: root without capabilities, cannot see `/etc/mini-deploy/env`, `apps/`, `ci.json` or the Docker socket. DB `/var/lib/mini-deploy/admin.db` (folder 700, file 600, both checked). Safari drops Secure cookies on http://*.localhost: use Chrome or Edge. Tests need `MINI_DEPLOY_ADMIN_DB` **and** `MINI_DEPLOY_TESTING=1`.
- Connected repos (P3b, `scripts/repos.py`, `scripts/admindb.py`): the repo list and each repo's own webhook secret live in `admin.db` (repo names never in git). Address `/webhook/<32-hex hook_id>`: the address picks the secret, the signature is checked before parsing, the payload repo must match the row; an unknown address is the same bare 401; a database error is 503 (logged), never a dropped connection. Secret shown once (connect / New secret), never on any page later. Repo names follow GitHub's rules (`REPO_RE`, also used by the webhook; `../etc` refused), unique ignoring case, checked and inserted in one `BEGIN IMMEDIATE`; app names used in `config/webhook.json` are refused; an existing app is taken over by the first push (the page says so). `kind=static` needs a sub-folder (never the repo root) with an `index.html` (else the push is refused and the live site stays); `.git` is removed and deploy.py's checks apply. A queued job whose repo was disconnected (or now maps to another app) does nothing (logged `disconnected`); previews stay until `deploy.py remove`. Queued pushes that cannot be checked because the DB is unavailable at startup are kept (`pending.bad`, logged `kept`), never dropped. GitHub token: `/etc/mini-deploy/github-token` (root 600, created once by hand; opened `O_NOFOLLOW|O_NONBLOCK`, checked before it is emptied), given to git only as `GIT_CONFIG_*` env (extraHeader for `https://github.com/`, `http.followRedirects=false`), scrubbed from git's errors; an unusable file is a `GitError`. **Accepted trade-off (owner, 2026-10-13):** the admin service can read the webhook secrets (in `admin.db`) and the token file (its one `ReadWritePaths` entry). That is weaker than P3a, where the admin could not see `/etc/mini-deploy/env`; the admin already runs as root and can roll back, and the webhook still builds only the branch tip. A copy of `admin.db` (or a backup) is a secret: keep it root-only.
- Uploads (P4, `scripts/upload.py`, `POST /api/upload/<app>` in `admin.py`): a .zip of a static site, at most 50 MB, sent as the request body (`Content-Type: application/zip`, never a form). Order: Host, exact Origin, `Sec-Fetch-Site`, content type, `Content-Length` (digits, <= 50 MB; else 413 unread, chunked 411), session (401) and CSRF (403) answered **without reading the body**, then the app name (APP_RE, not reserved, no `--`) and `repos.repo_for_app` (an app deployed from GitHub, in the DB or `config/webhook.json`, is refused 409). Only then: one upload at a time (409), the connection deadline extended to 120 s, a disk check (zip + 200 MB, + 200 MB more when the temp folder and `/sites` share a disk, + 100 MB), the body streamed to a 0600 file in the unit's private `/tmp` (never memory), refused if it took over 90 s. `upload.unpack` checks the whole zip before writing anything: end record read by hand first (the last `PK\x05\x06`, as zipfile does; zip64 refused; table of contents <= 1.5 MB, because that, not the claimed count, bounds zipfile's memory), <= 5,000 entries, <= 200 MB unpacked (also counted while writing), ratio <= 100:1 above 1 MB, names (no absolute, drive, `..`, `.`, empty part, `\`, control chars, part > 255 bytes, duplicates ignoring case, file/folder clash), types (no links, Windows reparse points, devices, FIFOs), no encryption, stored/deflate only, never `.env*`/`.git`/`.npmrc`/`.ssh`/`.aws` in any part (case-insensitive, `deploy._forbidden`). Files are written `O_EXCL|O_NOFOLLOW`, mode 0644; folders 0755; `__MACOSX` and `.DS_Store`-type junk skipped. Root = the zip's top, or its one top folder; `index.html` required. Then `deploy.deploy(app, root, lift_hold=True)`. Refusals after sign-in are audited `refused`; failures before deploying are a deploy-log line `upload ... fail`; a failed first upload leaves no empty `releases/` (`drop_empty_releases`); the temp folder is always removed. Static only: the admin service cannot reach Docker.
- A manual deploy, build or upload lifts a hold **inside the deploy lock** (`deploy.deploy(..., lift_hold=True)`): lifted after the lock is let go, it could erase the hold of a rollback made in that moment. A failure to lift it after the flip is only a warning.
- Every deploy, rollback and failure is one line in `/var/log/mini-deploy.log`. Release ids are UTC and always sort after existing ones.
- Tests never `rm -rf` inside scripts: they leave their `/sites/*-<pid>` apps and `/tmp/mini-deploy-*` folders, and the owner (or Claude, by a direct command) removes them.
- Tests never write into the real deploy log: unit tests point `deploy.LOG_FILE` at a temp file. (A fake `wa`/`wb` app once showed up on the dashboard as "needs a look".)
- **Never put a proxy, Funnel or `tailscale serve` in front of Caddy's :8080.** The logs page trusts "the connection comes from 127.0.0.1"; a local proxy would make every outsider look like 127.0.0.1. (Second gate: `@logs` also refuses requests carrying `X-Forwarded-For`, `Forwarded`, `X-Real-IP` or `Tailscale-*` headers.) The Funnel forwards only `/webhook` to :9000.
- Services (`systemd/`): the webhook runs sandboxed (`ProtectSystem=strict`, writable only `/sites /var/log /var/lib/mini-deploy /var/tmp /run`), never restart-loops on a config error (`RestartPreventExitStatus=1`), and its queue is saved to `pending.json` after every change (including the job being built), so a hard stop loses nothing. Build output is read in 64 KB chunks and printed only after cleaning.
- Build logs (`scripts/buildlog.py`): full output of every build in `/var/log/mini-deploy/builds/<app>/<UTC id>-<ok|fail>.log` (dir 0700), header lines then cleaned output (ANSI/control chars replaced, header values one line), at most 1 MB (start + end kept), newest 20 per app, ids always sort after existing ones. Shown ONLY at `logs.localhost` and only to connections from 127.0.0.1/::1 (Caddy `remote_ip`); never on the Wi-Fi, never on the Funnel. App name `logs` is reserved. The LAN dashboard keeps reason words only; its "view build log" links appear only when it is opened on `*.localhost`. Removing a preview deletes its logs. CLI: `scripts/logs.py`.
- Sites (`web/`): no external requests, no fonts or CDNs; dashboard JS uses `textContent` only (log lines hold build output); body text must reach 4.5:1 contrast (checked by `test-sites.sh`). `web/theme/pink.css` is the source; run `scripts/sync-theme.sh` after editing it. Caddy sends `Cache-Control: no-cache` so a deploy is visible at once.
